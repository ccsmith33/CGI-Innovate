## Executive Summary

The feed service simulation is mathematically sound for normal operations, but contains **ONE CONFIRMED CRITICAL BUG** that prevents backend integration. All other systems function as designed. The simulation will produce positive net growth at default settings, with DEFCON escalation and dependency penalties functioning correctly.

**Critical Finding**: The `BACKEND_URL` in `generator.py:18` defaults to `http://localhost:8000`, which **will fail in Docker** because container-to-container communication requires the service hostname (e.g., `http://backend:8000`). The logs showing "Push to backend failed: All connection attempts failed" confirm this bug is active. No events from the feed service are being persisted to the database.

## 1. BACKEND_URL Configuration & Docker Networking

### Finding: CRITICAL BUG - Incorrect Default

**File Reference**: `src/feed-service/app/generator.py:18`
```python
BACKEND_URL = os.getenv("BACKEND_URL", "http://localhost:8000")
```

**Docker Compose Analysis** (`docker-compose.yml`):
- The `backend` service runs on port 8000 inside the Docker network `sentinel-net` (line 54)
- The `feed` service also runs on the `sentinel-net` network (line 27)
- **The feed service is NOT passed a BACKEND_URL environment variable**
- Therefore, the feed service uses the default: `http://localhost:8000`

### Why This Fails in Docker

In Docker:
- `localhost` or `127.0.0.1` inside a container refers to that **container's own localhost**, not the host machine
- Container-to-container communication must use **service hostnames**
- The backend service is registered as hostname `backend` on the `sentinel-net` network
- Correct URL for feed→backend communication: `http://backend:8000`

### Impact

- **All events generated by the feed service fail to push to the backend**
- No ResourceLog records are created in the database
- Frontend sees zero resource events and zero historical data
- Database forecasts never recompute
- DEFCON broadcasts never reach frontend
- **Data integrity**: Feed simulation runs locally in memory but results are orphaned

### Proof from Logs

The error message "Push to backend failed: All connection attempts failed" (generator.py:160) indicates connection timeouts or refused connections, consistent with trying to reach `localhost` from inside a container.

### Recommended Fix

Add environment variable to `docker-compose.yml` feed service (line 15-27):
```yaml
feed:
  build:
    context: ./src/feed-service
    dockerfile: Dockerfile
  environment:
    - BACKEND_URL=http://backend:8000  # <-- ADD THIS
  ports:
    - "8001:8001"
  # ... rest unchanged
```

### DEFCON Escalation Triggers

**File Reference**: `src/feed-service/app/state.py:155-177`
```python
def compute_defcon() -> int:
    avg_health = sum(health_scores) / len(health_scores)
    critical_count = sum(1 for s in health_scores if s < 0.25)

    if avg_health >= 0.80 and critical_count == 0:
        return 5  # NORMAL
    elif avg_health >= 0.60 and critical_count <= 1:
        return 4  # ELEVATED
    elif avg_health >= 0.40 and critical_count <= 2:
        return 3  # GUARDED
    elif avg_health >= 0.20 or critical_count <= 3:
        return 2  # CRITICAL
    else:
        return 1  # OMEGA
```

**Health Score** = `current_stock / target_stock`

**At initial conditions** (all stocks = targets):
- All health scores = 1.0
- avg_health = 1.0 ≥ 0.80 ✓
- critical_count = 0 ✓
- **Result: DEFCON 5 (NORMAL)**

No dependencies trigger penalties at initialization.

## 7. Governor Interface & Production Rate Control

### Governor Command Interface

**File Reference**: `src/feed-service/app/main.py:71-82`
```python
@app.post("/control/production")
async def update_production(body: ProductionUpdate):
    key = (body.sector_id, body.resource_type)
    if key not in state.INITIAL_STOCKS:
        return {"error": f"Unknown sector/resource: {key}"}, 400
    state.set_production_rate(body.sector_id, body.resource_type, body.units_per_cycle)
    return {
        "sector_id": body.sector_id,
        "resource_type": body.resource_type,
        "units_per_cycle": body.units_per_cycle,
        "status": "updated",
    }
```

**Direct Control**: The feed service **directly accepts production rate changes** via HTTP POST to `/control/production`.

### State Update Function

**File Reference**: `src/feed-service/app/state.py:116-120`
```python
def set_production_rate(sector_id: str, resource_type: str, rate: float) -> None:
    with _lock:
        key = (sector_id, resource_type)
        if key in _production_rates:
            _production_rates[key] = rate
```

**No validation or capping**: The function accepts any rate value. No min/max constraints.

### Governor Integration Path

1. Governor sends HTTP POST to feed service's `/control/production` endpoint
2. Feed service updates `_production_rates` in memory
3. Next cycle (10 sec later), the new rate is applied to production
4. **Does NOT go through backend**—direct feed service control

**Conclusion**: Governor controls feed service directly. Backend is only involved in receiving/storing events, not in production control.

## 8. Cycle Timing & Push Events

### Cycle Interval

**File Reference**: `src/feed-service/app/generator.py:31`
```python
CYCLE_INTERVAL = 10.0  # 10 seconds real time = 1 simulation cycle
```

**Cycle frequency**: Once every 10 seconds.

### Main Loop

**File Reference**: `src/feed-service/app/generator.py:163-168`
```python
async def cycle_loop() -> None:
    """Main async loop: runs one cycle every CYCLE_INTERVAL seconds."""
    while True:
        await asyncio.sleep(CYCLE_INTERVAL)
        events = run_cycle()
        await push_events(events)
```

**Sequence**:
1. Sleep 10 seconds
2. Execute `run_cycle()` (synchronous, < 1ms)
3. Call `push_events()` (async HTTP POST, may take seconds)
4. Loop back to sleep

### Timing Issue Analysis

**Potential Issue**: If `push_events()` takes longer than expected or fails, the loop continues immediately to the next sleep without waiting. This is **by design** (no await for push result in the actual loop).

However, looking at the code flow:
- `await push_events(events)` is awaited, so the loop DOES wait for push to complete (successfully or fail)
- Even if push fails, the loop continues (push doesn't raise exceptions—see generator.py:160: "Failures are logged, not raised")
- **No timing issue detected**

### Event Generation During Push Failure

**Critical Finding**: When `push_events()` fails (which it does consistently due to the BACKEND_URL bug), events are still generated and stored locally in `state._events` (generator.py:107, 120, 142), but they never reach the backend database.

**File Reference**: `src/feed-service/app/state.py:61`
```python
_events: deque[dict[str, Any]] = deque(maxlen=MAX_EVENTS)
```

**Local event buffer size**: Last 500 events only. Events older than 500 cycles are discarded.
